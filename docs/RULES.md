# Правила проекта

## Непереговорные продуктовые правила

1. Email-интеграции нет. Email не вводится, не подтверждается, не хранится и не участвует в рефералах.
2. В Mini App нет административной панели, административных страниц или административного API для ручного редактирования каталога.
3. Товары и категории добавляются и редактируются через `assets/products.xlsx`. Синхронизация идёт по стабильному `sku`, а категории создаются из значений таблицы.
4. Будущий Google Sheets источник должен реализовать тот же контракт строк каталога; бизнес-логика импорта не должна зависеть от формата транспорта.
5. Все обработчики и состояния администратора Telegram находятся в `src/admin_flow.py`.
6. Все пользовательские обработчики и состояния Telegram находятся в `src/main_flow.py`.
7. Web-часть остаётся в этом Python-проекте: FastAPI, Jinja2, Tailwind и минимальный vanilla JavaScript. Node/npm и отдельный frontend workspace не добавляются.
8. Количество товара не показывается клиенту как постоянный остаток. Наличие и требуемое количество подтверждает администратор.
9. Telegram-профиль клиента хранится в полях `user_id` и `username`. Имя и фамилия заполняются из Telegram при первом создании клиента, после чего пользователь может менять их в профиле; номер телефона хранится как `phone_number`.

## Деньги и заказы

1. Все денежные значения хранятся как `Decimal`/`NUMERIC`, не `float`.
2. Скидка товара применяется до персональной скидки или промокода.
3. Персональная скидка и промокод взаимоисключающие.
4. Коины применяются после выбранной скидки; 1 коин = 1 рубль.
5. Партнёрское вознаграждение, доход, расход и прибыль начисляются только после подтверждения оплаты администратором.
6. Заказ хранит снимки SKU, названия, категории, розничной и закупочной цен, скидок, коинов и процентов на момент продажи.
7. Изменение Excel в будущем не меняет уже оплаченные заказы.
8. Для категории «Духи» чистая прибыль делится Диана 70% / Булат 30%; для «Электроника» — Булат 70% / Диана 30%. Проценты также должны сохраняться снимком.

## Безопасность и данные

1. Персональные операции Mini App доступны только по Telegram `initData` в заголовке `Authorization`; сервер проверяет его подпись на каждом запросе. Cookie и отдельные web-сессии не используются.
2. Админские Telegram-команды доступны только ID из `ADMIN_IDS`; одного username недостаточно.
3. Секреты передаются только через environment variables и не коммитятся.
4. Телефон, дата рождения и история заказов не попадают в логи без необходимости.
5. Любое изменение статуса оплаты должно быть идемпотентным и аудируемым.

## Инженерные правила

1. Поддерживаем Python 3.12+ и асинхронный I/O.
2. Базовые интеграции повторяют проверенный соседний проект: `Space`, `LoaderModule`, `DependenciesModule`, `LifecycleModule`, плагины `rewire_sqlmodel`, `rewire_fastapi` и `rewire_sqlmodel.ext.fastapi`.
3. Модели импортируют `SQLModel` из `rewire_sqlmodel`, а HTTP/Telegram транзакции используют `@transaction`.
4. Бизнес-расчёты отделяются от handlers и тестируются как чистые функции.
5. Импорт Excel сначала валидирует все строки, затем применяет изменения одной транзакцией. Пропавшие из полной таблицы товары скрываются, а не удаляются.
6. Публичные страницы должны быть mobile-first и учитывать цвета/viewport Telegram Web App.
7. Критическая бизнес-логика должна быть проверяема отдельно от transport-слоя; автоматические тесты будут добавлены на следующем этапе. Изменение покрытия требований отражается в `docs/PLAN.md` и `docs/TZ_AUDIT.md`.
8. Единственная рабочая СУБД проекта — PostgreSQL; локально приложение и БД поднимаются через Docker Compose.
